# Codexと一緒にServiceNowドキュメント活用リポジトリを育てた話

> note投稿用の下書きです。  
> この文章は、このリポジトリに残っているREADME、設計ドキュメント、ナレッジ記事、Git履歴をもとに、「私とCodexの過去のやり取り」を読み物として再構成したものです。

## はじめに

ServiceNowの調査や設計をしていると、公式ドキュメントを毎回ブラウザで探し、該当ページを開き、必要な箇所を読み、さらに社内向けの説明資料に落とし込む、という作業が何度も発生します。

もちろん公式ドキュメントは一次情報として重要です。しかし、ServiceNowの領域は広く、ITSM、ITOM、App Engine、AEMC、ReleaseOps、ATF、Instance Scan、DevOps Change Velocityなど、論点が横断的になると、ブラウザ上でページを行き来するだけでは整理しきれません。

そこで、ServiceNowのドキュメントをAIエージェントが読みやすいMarkdownリポジトリとして扱い、Codexと一緒に次のような作業ができる状態を目指しました。

- 公式ドキュメント相当のMarkdownを検索できる
- 複数ページを横断して論点を整理できる
- 顧客説明や社内提案に使える日本語資料を作れる
- ServiceNow開発・リリース運用のTo-Beを検討できる
- アップグレード時のSkipレコード対応など、実務ナレッジを蓄積できる

この記事では、このリポジトリをどのように作り、どのように使っているかを、Codexとの共同作業の流れとして紹介します。

## このリポジトリでやりたかったこと

最初に決めたコンセプトはシンプルです。

**ServiceNowのドキュメントを、人間が読むためだけでなく、AIエージェントが調査・要約・設計支援に使える形にする。**

READMEにも、このリポジトリはServiceNow AI Platformの製品ドキュメントをAI Agent consumption向けに最適化したもの、と説明されています。また、画像などのメディアは含めず、Markdownを中心に扱う方針にしています。

この方針にすると、Codexに対して次のような依頼がしやすくなります。

- 「AEMCとReleaseOpsの役割分担を整理して」
- 「GitHub連携を前提に、App Engine開発の標準フローを作って」
- 「更新セット、Application Repository、XML資材をどう扱うべきか提案して」
- 「Skipレコード管理の実務手順を日本語でまとめて」

つまり、単なるドキュメント置き場ではなく、ServiceNowに関する調査・設計・ナレッジ化の作業場所として使うことを狙いました。

## 作り方1: まずはAIが読める情報源を用意する

リポジトリの基本構成は、ServiceNowの各プロダクト領域ごとにMarkdownファイルを配置する形です。

READMEには、Australiaリリースファミリーのドキュメントとして、Account Lifecycle Events、Building applications、IT Service Management、Service Exchangeなど多数の出版物へのリンクが並んでいます。

また、`llms.txt`には、AIエージェント向けの利用メモとして次のような前提が整理されています。

- リリースごとにGitブランチを分ける
- `australia`が最新リリースである
- 各Markdownファイルには、タイトル、製品領域、更新日、canonical URLなどのメタデータがある
- ServiceNow公式サイトはJavaScript SPAであり、AIが直接読むには向かないため、Markdownファイルを参照する

この`llms.txt`があることで、Codexは「どこを見ればよいか」「どのブランチを前提にすればよいか」「公式サイトを直接スクレイピングしようとしないこと」を理解しやすくなります。

## 作り方2: 調査結果をそのまま捨てず、提案書として残す

次に行ったのが、ServiceNowのモダン開発環境に関するTo-Be提案の作成です。

Codexとのやり取りでは、AEMC、ReleaseOps、GitHub、ATF、AutomatePro、Application Repository、更新セット、XML資材といった要素を横断し、現実的な開発・テスト・リリース運用に落とし込んでいきました。

最終的には、`servicenow-modern-development-environment`フォルダーに、次のような分割ドキュメントとして整理しています。

- 概要、As-Is、設計原則
- To-Be全体像
- 資材タイプ別フロー
- 品質ゲートと自動テスト
- GitHub運用
- 段階的移行ロードマップ
- RACI、KPI、設計根拠
- ビジュアルHTML版

ポイントは、Codexに「一発で完璧な資料を書かせる」のではなく、会話しながら論点を増やし、あとから分割・再構成して、読みやすい資料群にしたことです。

最初は大きな提案書として作り、その後、読みやすい単位に分割しました。これにより、レビューする人は必要な章だけを読めますし、Codexに追加修正を依頼するときも対象ファイルを絞りやすくなります。

## 作り方3: 「きれいな理想論」ではなく、現場の例外を扱う

ServiceNowの開発運用を考えるとき、理想論だけでは足りません。

たとえば、スコープアプリはGitHubとApplication Repositoryで管理できても、グローバルスコープ変更は更新セットが中心になります。さらに、ユーザー、グループ、ロール、マスターデータ、環境依存値など、更新セットやアプリ成果物だけでは扱いにくいデータもあります。

そこで、XML資材については「すべて禁止」ではなく、次のように分類する方針にしました。

1. スコープアプリへ包含できるもの
2. 更新セットへ包含できるもの
3. Import SetやTransform Mapで扱うべきマスターデータ
4. Runbook taskとして管理する環境依存作業
5. どうしても残るXML例外

この整理は、Codexとのやり取りでかなり重要だった部分です。

AIに依頼すると、時々「全部CI/CD化しましょう」「全部Gitで管理しましょう」のような理想形に寄りがちです。しかし、ServiceNowの現場では、移送対象にならないデータ、環境ごとに異なる設定、手順化せざるを得ない作業が残ります。

そのため、このリポジトリでは「自動化できないものも、未管理にしない」という考え方を明文化しました。

## 作り方4: 実務ナレッジを`knowledge`に貯める

提案書とは別に、実務で何度も使いそうな内容は`knowledge`フォルダーに切り出しています。

その例が、ServiceNowメジャーバージョンアップ時のSkipレコード管理方法です。

Skipレコードは、ServiceNowの標準更新と顧客カスタマイズが衝突したときに、標準更新を自動適用せずレビュー対象として残す仕組みです。

このテーマについても、Codexに対して「実務向けに整理して」と依頼し、次のような観点でまとめました。

- Skipレコードとは何か
- Upgrade HistoryやUpgrade Monitorでどこを見るか
- Retain、Merge、Revert、Reviewedの使い分け
- 優先順位の付け方
- 管理台帳に持つべき項目
- 本番アップグレード前の完了条件

このように、1回の調査で終わらせず、次回以降も再利用できるナレッジとして残していくのが、このリポジトリの使い方です。

## 使い方1: Codexに「リポジトリ内を根拠に」聞く

このリポジトリの一番基本的な使い方は、Codexにリポジトリ内のMarkdownを根拠として調査してもらうことです。

たとえば、次のように依頼します。

```text
AEMCとReleaseOpsの役割分担を、このリポジトリ内のドキュメントを根拠に日本語で整理してください。
```

または、もう少し具体的にします。

```text
ServiceNowのスコープアプリ開発で、GitHub、Application Repository、ReleaseOpsをどう使い分けるべきか、
顧客説明向けの資料としてまとめてください。
```

このとき大事なのは、Codexに「一般論」ではなく「このリポジトリ内の情報を根拠に」と明示することです。

そうすると、公式ドキュメント相当のMarkdownや、すでに作成済みのTo-Be提案を参照しながら、より一貫した回答になります。

## 使い方2: 調査、設計、文章化を分けて依頼する

Codexに依頼するときは、いきなり完成文章を求めるより、次のように段階を分けると使いやすいです。

### 1. まず調査させる

```text
AEMC、ReleaseOps、Developer Sandboxes、DevOps Change Velocityに関係するMarkdownを探し、
それぞれがServiceNow開発運用で何を担当する機能なのか整理してください。
```

### 2. 次に論点を整理させる

```text
9インスタンス構成の現行ServiceNow開発環境を前提に、
どの機能をどのフェーズで導入すべきか、論点とリスクを整理してください。
```

### 3. 最後に資料化させる

```text
上記をもとに、顧客説明用のTo-Be提案書としてMarkdownで作成してください。
章立ては、概要、As-Is課題、To-Be、移行ロードマップ、RACI、KPIにしてください。
```

この流れにすると、Codexの出力を途中でレビューしやすくなります。

## 使い方3: 大きな資料は分割して育てる

長い提案書を1ファイルで管理すると、後から修正しにくくなります。

今回のリポジトリでは、ServiceNowモダン開発環境のTo-Be提案を複数ファイルに分割しました。

この分割には、次のメリットがあります。

- 章ごとにレビューしやすい
- Codexへの修正依頼で対象範囲を限定できる
- Gitの差分が読みやすい
- 顧客説明時に必要な章だけ抜粋できる
- 将来、別の記事や提案書に再利用しやすい

たとえば、品質ゲートだけを見直したい場合は、`04-quality-gates-and-testing.md`を対象にすればよいです。GitHub運用だけ直したい場合は、`05-github-operations.md`を対象にできます。

AIとの共同作業では、ファイル分割はかなり重要です。大きな文書を一気に直すより、小さな文書を何度も改善するほうが、精度もレビュー効率も上がります。

## 使い方4: Git履歴を「作業ログ」として使う

このリポジトリでは、Codexとの作業結果をGitコミットとして残しています。

Git履歴を見ると、次のような流れが見えます。

- リポジトリを作成する
- メディアファイルを除外する
- ServiceNowモダン開発環境フォルダーを作る
- 提案書を分割し、AutomateProのテスト計画を追加する
- Skipレコード管理ガイドを追加する

この履歴があることで、「どのようにリポジトリが育ってきたか」を後から説明できます。

今回のnote記事も、まさにこの履歴とファイル構成をもとに書いています。

## Codexに依頼するときのコツ

実際に使ってみて、Codexへの依頼にはいくつかコツがあると感じました。

### 1. 前提条件を具体的に書く

ServiceNowは組織や環境によって構成がかなり異なります。

そのため、次のような前提を最初に渡すと、出力の精度が上がります。

- Dev環境が何台あるか
- 検証、Pre-Prod、本番の役割
- App Engine中心なのか、ITSM/ITOM中心なのか
- 更新セット、Application Repository、GitHubの現行利用状況
- XML手動Importが残っているか
- ATFやAutomateProを使っているか
- 国外チームが関与するか

### 2. 「禁止したいこと」も書く

たとえば、次のような制約を明示します。

- 本番インスタンスで直接開発しない
- GitHubから本番へ直接Pullしない
- XML手動Importを無管理にしない
- 検証環境で修正して、そのままPublishしない

禁止事項を明示すると、Codexが現場に合わない理想論へ寄りにくくなります。

### 3. 最初から完成版を狙わない

最初の出力は、たたき台で十分です。

その後、次のように依頼して育てていきます。

```text
この提案は理想論に寄りすぎています。
既存の更新セット運用とXML例外が残る前提で、段階移行案に直してください。
```

```text
Platform Ownerが個別アプリの実装責任まで持っているように見えます。
RACIを見直し、PFOはプラットフォーム標準と統制に責任を持つ形にしてください。
```

```text
AutomateProはServiceNow標準機能ではないので、ReleaseOpsとの連携はRunbook taskから始める現実的な案にしてください。
```

このように、違和感を具体的に伝えるほど、資料は実務向けになります。

## このリポジトリを使うメリット

このやり方の良いところは、AIとの会話が一過性で終わらないことです。

普通にチャットで質問すると、その場では便利でも、後から同じ話を再利用しにくくなります。

しかし、リポジトリにMarkdownとして残しておけば、次のような使い方ができます。

- 過去の調査結果を再利用する
- 顧客やチーム向けに整形して共有する
- Gitで変更履歴を追う
- Codexに過去資料を読ませて追加修正する
- 別テーマの記事や提案書に展開する

つまり、AIとのやり取りを「会話」から「資産」に変えられます。

## 今後やりたいこと

今後は、このリポジトリをさらに次の方向に育てたいです。

- ServiceNowアップグレード手順の標準化
- ReleaseOps Playbookテンプレートの作成
- Skipレコード管理台帳テンプレートの追加
- ATF/AutomateProテスト観点テンプレートの追加
- GitHub PRテンプレートやCODEOWNERS例の追加
- 顧客説明用の図解資料の充実
- note記事として公開しやすい短縮版の作成

ServiceNowの開発・運用は、プロダクト知識、開発プロセス、リリース統制、変更管理、テスト、監査が複雑に絡みます。

だからこそ、AIに丸投げするのではなく、AIが参照できる情報源と、作業結果を蓄積する場所を用意することが大事だと思っています。

## まとめ

このリポジトリは、ServiceNowドキュメントをMarkdownとして扱い、Codexと一緒に調査・設計・資料化・ナレッジ化を進めるための作業場です。

作り方のポイントは、次の通りです。

1. AIが読めるMarkdownの情報源を用意する
2. `llms.txt`でリポジトリの前提を明文化する
3. 調査結果を提案書やナレッジとして残す
4. 大きな資料は章ごとに分割する
5. Git履歴を作業ログとして残す
6. Codexには前提、制約、違和感を具体的に伝える

Codexを使うと、ServiceNowのような広い領域でも、調査から文章化までのスピードをかなり上げられます。

ただし、本当に価値が出るのは、AIの回答をその場限りにせず、リポジトリに残し、何度も改善できる形にしたときです。

このリポジトリは、そのための実験であり、実務に使えるナレッジベースでもあります。
